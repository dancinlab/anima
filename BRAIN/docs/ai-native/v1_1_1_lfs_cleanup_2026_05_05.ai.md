# v1.1.1 large-file history purge — hexa-brain (2026-05-05)

## TL;DR

- **Option chosen**: B (`git filter-repo --invert-paths`), NOT C (LFS migrate)
- **Rationale**: corpus files were already absent from working tree at v1.1.0 HEAD
  — only history retained the blobs. LFS migration would have required first
  restoring the files just to re-track them; pure history purge is cleaner.
- **Files purged**: `data/corpus_v2.txt` (67MB) + `data/corpus_v5.txt` (100MB)
- **Repo size**: local `.git/` 190M → 130M after gc; remote pack will shrink
  on GitHub-side gc as orphaned commits expire
- **v1.1.1 tag**: pushed to origin (`9411ab0e` annotated → `3687c703` commit)
- **Old tags retargeted**: v1.0.0 (`1ffd00ee`→`aaebac74`) and v1.1.0
  (`279bb38f`→`f1e79b4b`) force-updated on origin to point at the rewritten
  equivalents — required so GitHub doesn't keep corpus blobs reachable through
  old tag refs

## §3 Honest C3 (≥5)

1. **History rewrite is destructive and irreversible.** Every commit hash from
   the spinoff onward changed (e.g. v1.1.0 head `d75f7c3d` → `e9cd115a`).
   Anyone who cloned hexa-brain between 2026-05-04 (v1.1.0 push) and
   2026-05-05 (this v1.1.1 push) has a divergent local copy and must reclone
   or perform a manual rebase. Standard practice for repos this fresh, but
   undeniably a one-way door.
2. **Force-push to `main` was required.** Used `--force-with-lease` (safer
   than `--force`) to ensure no concurrent push lost. Two additional
   `--force` pushes were needed for tags v1.0.0 and v1.1.0 to retarget the
   tag pointers — `--force-with-lease` is not supported per-tag in stock git,
   so `--force` was used. Acceptable since this repo has a single maintainer
   and origin had not received intervening pushes (verified via `ls-remote`
   pre-push).
3. **GitHub-side gc latency**: orphaned commits + corpus blobs persist on
   GitHub's storage even after our force-push, until GitHub's internal gc
   sweeps unreachable objects. Window is typically days–weeks.
   `git push --dry-run origin main` returns "Everything up-to-date" so no
   user-visible warning, but the blobs are addressable by SHA via API for a
   transitional period. To force immediate gc, would require GitHub support
   ticket — not pursued (low value, files were not secrets).
4. **Local `.git/` shrank only 190M → 130M after gc**, not the dramatic drop
   one might expect from purging 167MB of corpus blobs. Reason: local refs
   `hexa-brain-core` (`89ed8d68`), `hexa-brain-eeg` (`fbeb8c1d`), and
   `anima-source/*` remote-tracking branches still reference pre-rewrite
   commits with the corpus blobs reachable. These were preserved as
   intentional spinoff bookkeeping (per CRITICAL guard "DO NOT push if
   dry-run shows unexpected losses"). To shrink further locally, delete
   those refs and re-gc — left as future cleanup, not in scope here.
5. **Option choice subjective**. Option C (LFS migrate) would have preserved
   the corpus files as accessible LFS pointers, useful if downstream
   consumers wanted them. We chose Option B because (a) the files were
   already removed at HEAD intentionally, (b) corpus_v5 was specifically
   noted in v1.0.0 spinoff handoff as published to R2 (external storage
   already exists), (c) LFS Hub usage incurs bandwidth quota that could
   surprise users, and (d) BFG/filter-repo is GitHub's own recommended
   path for "I committed a large file by accident." Reasonable engineers
   could argue C; B is defensible.
6. **Tag retargeting is unusual**. Most repos leave old tags pointing at
   pre-rewrite commits (since tags are "immutable historical markers" by
   convention). We force-updated v1.0.0 and v1.1.0 to defeat the corpus-blob
   reachability path. Tradeoff: any external doc citing `git checkout v1.0.0`
   gets a different tree than originally tagged (corpus files absent). For
   hexa-brain this is acceptable — corpus files were never the value being
   tagged — but a pedantic reader could call this a tag-history violation.
7. **No CI/CD validation in this repo**. Spec said "no warnings on dry-run" —
   confirmed. But we have no automated test that imports/loads either tag
   to confirm code still works post-rewrite. Manual `git status` on cleaned
   tree showed nothing-to-commit; CLI tools depend only on `core/` and `eeg/`
   subsystem code which was untouched by filter-repo (only path filter was
   `data/corpus_v{2,5}.txt`).
