SCOPE OF PORT
-------------
The tier-C smoke harnesses (training/hxblas_cuda_smoke.c +
hxblas_cuda_smoke_large.c) exist to diff a vendor GEMM (hxblas_sgemm,
cuBLAS/Accelerate-cblas) against a PURE scalar CPU reference. Per the M1
INVENTORY these are "SMOKE/TEST — retirable once an equivalent hexa-native
smoke covers hxblas_sgemm" (milestone M3). Their PORTABLE core — the only
non-vendor logic they carry — is:
  - deterministic input pattern  A[i]=0.02*((i*37)%131-65), B[i]=0.02*((i*53)%127-63)
  - scalar reference matmul      C_ref = op(A)·op(B) honouring transA/transB
  - fp32 accumulation + max_err reduction
That core is hexa-portable (no cuBLAS/cuda/cblas call). hxblas_sgemm
itself is the irreducible tier-A vendor bridge and is NOT ported.

Ported file:  training/native/sgemm_ref_native.hexa
C baseline:   training/native/sgemm_ref_runeq.c   (computes the identical
              per-case summary: fp32 sum + max abs element, which together
              pin every C_ref element the matmul produced).

HEXA SIDE — BLOCKED BY TOOLCHAIN (could NOT run; not a port-logic fault)
-----------------------------------------------------------------------
hexa 0.1.0-dispatch has RETIRED the interpreter ("hexa run" = compile-then-
exec); EVERY execution path goes through native codegen. Two independent
defects in that toolchain block running the ported matmul. Both were
isolated to MINIMAL reproducers and CONFIRMED on BOTH pool hosts:

BUG 1 — `while` loop mis-compiles to a NON-TERMINATING loop (runtime hang).
  Reproducer (training/native/repro/hexa_while_hang.hexa):
    fn main() {
        let kk = 0
        while kk < 4 { kk = kk + 1 }
        println("kk=" + str(kk))
    }
  `hexa build` succeeds; the produced native binary HANGS (timeout 124) and
  prints nothing. Confirmed on aiden AND summer. `for i in 0..N` range
  loops compile + run correctly (verified) — so the defect is specific to
  `while` codegen.

BUG 2 — parser crash "index 0 out of bounds (len 0)" on a nested-`for`
  accumulator pattern (a `let` declared in a fn body whose value is
  mutated inside a deeper nested `for`, itself inside an outer `for`).
  Minimal reproducer (training/native/repro/hexa_nestfor_parsecrash.hexa):
    fn f(m,n,k) {
        for i in 0..m {
            for j in 0..n {
                let s = 0.0
                for kk in 0..k { s = s + 1.0 }
                println(str(s))
            }
        }
    }
    fn main() { f(2,2,2) }
  `hexa parse` / `hexa build` abort with "index 0 out of bounds (len 0)";
  no C is emitted. A double-`for` (tA), a flat `for`+`if/else` (tB/tC), and
  even 7 sibling for-loop functions (n7) all parse cleanly — so the trigger
  is the SPECIFIC triple-nest-with-interleaved-let shape, not loop count.
  This is exactly the matmul shape (i × j × k with a per-(i,j) fp32
  accumulator), so the port cannot avoid it. Factoring the inner loop into
  a helper (sgemm_ref_native.hexa uses one-`for`-per-fn: dot/fill_row/
  matmul/summarize_*) still trips the same crash at file scale.
