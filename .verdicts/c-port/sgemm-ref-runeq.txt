ROOT-CAUSE 1 — NEW const-fold MISCOMPILE (sibling of #2650, NOT covered)
-----------------------------------------------------------------------
`maxabs` is wildly wrong in all 8 cases. The cref ELEMENTS are PROVEN
byte-identical to C (dumped + compared, 16x16 tA0tB0: max element abs =
6.2588 in BOTH). The miscompile is in the reduction:
    let maxabs = 0.0
    for idx in 0..total { ... if av > maxabs { maxabs = av } }
A PLAIN `let` (non-mut) reassigned inside an IF-body within a FOR-loop
has its comptime-const fold inlined into the IF CONDITION (`av > 0.0`,
always true) → maxabs always overwritten → ends holding the LAST
element's abs (case1: |cref[255]| = 1.0392, exactly the reported value).
Isolated repro (with cref[0]=6.2588 set explicitly) returns 1.0392.
Changing `let maxabs` → `let mut maxabs` FIXES maxabs (8/8 match).
This is the SAME class as #2650 BUG2 (while-condition fold inlining a
reassigned binding) but for an `if`-condition whose body reassigns the
folded var — the #2650 pre-invalidation does NOT cover the if-arm.
=> A second codegen fix is warranted in hexa-lang self/codegen.hexa
   (pre-invalidate comptime-const fold for vars reassigned in if/elif
   bodies BEFORE emitting the if condition, mirroring the while fix).

ROOT-CAUSE 2 — inherent fp-CONTRACTION (FMA) DIFFER (NOT a compiler bug)
-----------------------------------------------------------------------
Even after the `mut` fix lands maxabs 8/8, `sum` STILL DIFFERS by ~1 ULP
in 4 cases (tA1tB1 + all three 128-cases). Cause: the C reference built
with `cc -O2` CONTRACTS `s += a*b` into a fused multiply-add (single
rounding of s + a*b). The hexa port models fp32 explicitly as
`round_f32(s + round_f32(av*bv))` — it rounds the product SEPARATELY,
which a contracted FMA does not. Confirmed: rebuilding the C ref with
`-ffp-contract=off` shifts the C output too (case1 5.7592 -> 5.75921),
proving FMA was active. The product step itself is NOT double-rounding
(0/16637 product mismatches), so the divergence is purely the
contracted s+=a*b vs explicit-double-round add. This is a genuine
fp-SEMANTICS mismatch between the port's explicit-rounding model and the
C baseline's compiler-contracted arithmetic — NO `mut` fix and NO
codegen fix resolves it; it is baseline-fp-flag-dependent (the pool-linux
gcc baseline in M3-sgemm_ref.txt already shows DIFFERENT values:
sum=5.75921 / -1.40519, matching the -ffp-contract=off variant).
=> Value-exact RUNEQ is NOT achievable as-specified; the port and the C
   baseline would need a pinned, contraction-free fp contract on BOTH
   sides (e.g. C compiled `-ffp-contract=off` AND a hexa fma/no-contract
   model) to be byte-exact. As authored, the verdict is DIFFER.
