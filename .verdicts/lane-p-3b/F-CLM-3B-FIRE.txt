Resuming the arc (Stage 0/1 landed: #1753 #1754 #1756), the first 3B fire attempt
OOM'd on the H100 at EVERY batch size — even bs=1/seq=512 tried a single 64 GiB
allocation. A layer-by-layer memory probe (verbatim, /tmp/probe_layer.out) localized it:

  PARAMS 3072954654
  embed 12.30GB ... trunk[0] 12.56GB ... trunk[10] 13.81GB ... trunk[20] 49.35GB
  ERR CUDA out of memory. Tried to allocate 64.01 GiB ... at model.py:104  x = F.pad(x, (self.pad, 0))

ROOT CAUSE (architecture, NOT a tuning issue): the trunk dilation grows as
`dilation_base**i` (=2**i). At n_trunk_layers=30 this reaches 2**29 = 536,870,912
at the last layer; the causal left-pad = (kernel-1)*dilation = 2*dil, so a layer
pads a (1,4096,512) tensor by ~10**9 zeros — a multi-GB buffer that sees NO real
taps (every dilated tap lands in padding once dilation >= seq_len). The d768 GOLDEN
had L=1 (max dilation 2**0=1) so this never surfaced before scaling L.

FIX (a_completeness_over_cheap — fixed at the root, not worked around):
cap the dilation: `dilation = min(dilation_base**i, max_dilation)` with
max_dilation=512 (>= seq window). Applied IDENTICALLY in BOTH:
  · CLM/model/model.py  (CLMConfig.max_dilation=512 + the dils list)
  · CORE/clm_decode.hexa (DIL_CAP=512 in the L-trunk loop)
so a deep-L .clm decodes on the ENGINE exactly as it trained.

BYTE-EQ PRESERVED (the cap touches runtime dilation only, never serialized bytes;
min(2**0,512)=1 at L=1 → golden unchanged). Re-verified verbatim (CLM/model/verify_clm_v2.py):
  F-CLM-V2-ROUNDTRIP=1
