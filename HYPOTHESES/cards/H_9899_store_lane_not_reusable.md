## 왜 확인해야 했나

[[H_9898]] 은 *'조성을 `--store-bridge` 같은 별도 lane 에 두는 것이 프런티어'* 라고 적었다.
그 문장은 **그 lane 이 조성을 실을 수 있다는 가정**을 담고 있고, 검증 없이 두면
다음 사람(또는 미래의 나)이 하루를 태운 뒤에야 발견한다. 코드에서 확인했다.

## 확정 — lane 은 구조적으로 **이진 readout** 이다

`StoreBindCell` 이 만드는 학습 창은 답의 **첫 바이트 하나**만 담는다:

```python
seq = b" " * (T - len(prompt)) + prompt.encode() + gold[:1].encode()   # ← gold[:1]
```
주석도 명시한다: *"binary readout needs only the first byte at qpos"*,
*"the answer tail spelling is not in the window"*.

| | |
|---|---|
| store lane 이 읽는 것 | **1 바이트** |
| rule-compound 답 길이 | 4~6 바이트 (평균 5.2) |

⟹ 첫 바이트만으로는 조성을 판정할 수 없다. 20 어간의 앞절반 첫 글자가 겹쳐
(`m`·`t`·`s` 각 2개) **우연 적중이 크고**, `ρ·weave` 의 문자열 포함 채점과도 맞지 않는다.

**답을 1바이트로 줄이는 우회도 불가**하다 — 1바이트 목표는 `ρ·weave` 에서 우연 적중률이
너무 높아 통제가 의미를 잃는다.

## 🔎 결론 — 새 lane 이 필요하다 (재사용 아님)

[[H_9898]] 의 방향(**분리**)은 유효하나, 그 구현은 `--store-bridge` **재사용이 아니라**
**다중바이트 답을 지원하는 새 lane**이다. 필요 요건:
1. CE 가 트렁크에 닿지 않을 것(store lane 의 핵심 성질 — 이건 그대로 차용 가능)
2. **답 전체(다중 바이트)** 를 목표로 할 것 ← store lane 이 못 하는 부분
3. `ρ·weave` 채점(문자열 포함)과 정합할 것
