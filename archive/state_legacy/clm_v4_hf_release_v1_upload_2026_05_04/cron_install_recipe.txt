WHY MANUAL RUN IS PREFERRED (DO NOT INSTALL CRON)
-------------------------------------------------
1. One-shot scope. This cleanup is for a single upload cycle (clm-v4-mk2-v1 v1 upload). Cron's value is recurring schedule — a one-shot job in cron is anti-pattern; `at` would be slightly more appropriate, but still inferior to operator-driven manual run.

2. Two gates require human judgment in failure cases. GATE 1 (review window elapsed) is a strict timestamp check — fine for cron. GATE 2 (HF repo intact: siblings=15 + commit_sha matches) — if siblings drift to 14 or 16, OR if commit_sha changes (re-push), the script aborts; cron'd execution would silently fail unless cron output is monitored, whereas an operator running manually sees the abort message immediately and can decide whether the drift is intentional (re-push happened, update expected sha) or surprising (repo tampered, escalate).

3. Pre-push leak guard / sanity F-CLM-RELEASE-1 + F-CLM-RELEASE-2 SHOULD complete BEFORE cleanup. These are user-driven sanity tests during the review window:
   - F-CLM-RELEASE-1: AutoModelForCausalLM.from_pretrained(repo, trust_remote_code=True) on fresh shell
   - F-CLM-RELEASE-2: 1-batch forward returns finite logits shape [1,T,64000]
   If user has not run these by 2026-05-07, automatic cleanup may delete the staging dir before they have a chance to re-upload from staging if a fix is needed. Manual run lets operator confirm sanity tests passed first.

4. Cleanup operates over SSH to ubu1. Cron-driven SSH requires either passwordless key + agent forwarding (security exposure) or key-with-passphrase + ssh-agent unlock (won't survive cron's bare environment). Manual operator run already has ssh-agent available in interactive shell.

5. Memory feedback feedback_cleanup_bg_guards.md mandates verb-classified cleanup with pre+post state verification. Cron-driven invocation cannot interactively answer "is this drift intentional?" prompts; manual run can.
