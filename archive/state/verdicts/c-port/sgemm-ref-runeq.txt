ROOT-CAUSE 1 — if-body const-fold MISCOMPILE (CONFIRMED COMPILER BUG, FIXED)
---------------------------------------------------------------------------
`let maxabs = 0.0` (a plain immutable let) const-folds maxabs -> 0.0. The
reduction `for idx ... { if av > maxabs { maxabs = av } }` inlined the STALE
literal 0.0 into the IF CONDITION (`av > 0.0`, always true for positive av)
while the body reassigned the live maxabs -> the reduction kept the LAST
element instead of the MAX. Same CLASS as #2650 BUG 1 (while-condition fold
inlining a reassigned binding) but for an IfExpr at statement position whose
then/elif/else body reassigns the folded var — #2650's WhileStmt
pre-invalidate did NOT cover the if-arm.
FIX (hexa-lang self/codegen.hexa, ExprStmt/IfExpr arm of _gen2_stmt_inner):
pre-invalidate the comptime-const fold for every name the then_body + else_body
reassign (via _gen2_collect_assigned, which recurses into else_body so chained
elif/else arms are covered) BEFORE comptime-folding or emitting the condition,
mirroring the WhileStmt pre-invalidate at ~L3496. Regression catcher m10
(self/test/miscompile_class/m10_if_body_fold_reassign.hexa). hexa-lang PR:
mczero/if-body-fold-fix (base=main). With the fix, maxabs is correct 8/8.

ROOT-CAUSE 2 — fp32 MODEL MISMATCH (HARNESS FIX, not a bug)
----------------------------------------------------------
After fix 1, maxabs matched 8/8 but the SUM (and the per-element matmul)
still differed. Element-bit measurement showed the divergence is a THREE-part
fp-semantics mismatch between the C reference and the port's fp32 model — NOT
a single FMA contraction:
  (a) INPUT: port fills r32(0.02 * (double)int) — 0.02 is an f64 constant;
      the C ref used 0.02f (the f32 literal, != (double)0.02) -> 67/256
      input elements differed by 1 ULP before any matmul.
  (b) PRODUCT: port forms a*b in f64 then rounds to f32; C used f32-native
      a*b.
  (c) ACCUMULATE: port rounds to f32 after EVERY add (no FMA); C -O2 fused
      `s += a*b` into a single-rounded FMA.
The port has no native f32 type (hexa Float is f64) and models fp32 by an
explicit round-to-binary32 (write_f32/deref_f32) at each materialise with f64
arithmetic between rounds. A faithful RUNEQ must pin the SAME fp model on both
sides. FIX (training/native/sgemm_ref_runeq.c, HARNESS): introduce r32() =
(float) and rewrite the driver to the port's model — f64 0.02 constant,
f64 product rounded to f32, f64 accumulate rounded after every add — and build
with `cc -O2 -ffp-contract=off` so the compiler cannot re-fuse the explicitly
rounded add into an FMA. This is a harness fp-contract alignment, not a port
or compiler change.
