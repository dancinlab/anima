# § 7 — honest_limits (≥ 4)

- **L1 grep 한계**: `grep "^fn .*entropy"` 는 정의만 잡고 **inline body** (e.g., `phi_entropy` 의 13 lines 가 다른 H 에 손으로 풀어 적힌 케이스) 는 fluent 비검출. 실제 sweep-able sites 는 본 표 dup 수의 1.3–1.8 배로 추정.
- **L2 domain-specific 판정의 주관성**: `_run_ca` 를 "wolfram_ca" 로 promote 할지 LIFE-specific 으로 둘지 모호. binary vs density variant 가 substrate 가정에 묶임 → ★★ 부여했으나 ★ 로 강등될 여지.
- **L3 cross-repo coordination 시점**: hexa-lang/stdlib/iit_ei.hexa 는 이미 PR-only landing (atlas SSOT 정책). anima 측 분해 → hexa-lang upstream patch 라운드 트립 발생 — stdlib promote PR 한 묶음에 모아 fire 권장. 본 survey 는 timing 결정 안 함.
- **L4 binary/density variant 의 통합 비용**: H_215 `_run_ca_binary` vs `_run_ca_density` 는 같은 surface 가 아닌 다른 update rule 두 surface — wolfram_run_ca 라는 단일 fn 으로는 안 됨 (kind 인자 추가 필요). 17 dup 중 일부는 strict 동일성 부재.
- **L5 farr vs list dual surface 비용**: anima 측 `_mean` 의 11 dup 중 (a) farr handle + n vs (b) `[float]` literal 두 signature 가 섞임. stdlib 으로 promote 시 두 surface 중 어느 것을 canonical 로 할지 결정 필요 (RFC 036 byte-equal anchor 는 farr 쪽).
- **L6 log2 vs log/ln 의 안전성**: hexa runtime 의 `log(x)` 는 base-e (확인됨, phi_native.hexa:107 `log(2.0)` = ln(2) ≈ 0.693). `log2(x) = log(x) / log(2.0)` 는 매 호출마다 `log(2.0)` 재계산을 inline 으로 풀면 비효율 → stdlib 의 log2 는 `ln2_inv = 1.4426950408889634` 상수 활용 권장 (이미 iit_ei.hexa 에 `LN2_INV` 있음 → 재활용).
